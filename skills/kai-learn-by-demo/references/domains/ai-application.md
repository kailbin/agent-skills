# Domain：AI 应用

适用于：在应用中集成大模型的技术，例如 LLM API、Spring AI、LangChain、LangChain4j、RAG、Agent、工具调用、MCP、Embedding 与向量数据库、记忆（Mem0）、语音（ASR / TTS）。

> 这份 domain 还没有经过实际项目的检验。第一次使用后，按 SKILL.md 第 7 步把经验沉淀回来。

## 1. 知识点维度

| 级别 | 维度 | 说明 |
|---|---|---|
| L1 | 模型调用 | 同步 / 流式调用、消息角色、参数（温度、最大 token）、结构化输出 |
| L1 | Prompt | 模板、few-shot、系统提示；对比不同写法的输出 |
| L1 | 抽象层 | 框架的 ChatModel / ChatClient 等抽象，以及怎样切换模型供应商 |
| L2 | 工具调用 | 定义工具、模型选择工具、执行与回填结果 |
| L2 | RAG | 文档切分 → Embedding → 向量库 → 检索 → 拼接上下文；每一步一个模块 |
| L2 | 记忆与会话 | 对话历史的存储、截断与摘要 |
| L2 | Agent / MCP | 多步推理、工具编排、MCP Server / Client |
| L3 | 协议与框架内部 | **不用框架、直接用 HTTP 调用模型 API**，手写一个最小的工具调用循环 / RAG 流程，与框架的结果对照 |
| L3 | 向量检索 | 相似度计算、近似最近邻索引；手写暴力检索并与向量库的结果对比 |
| L4 | 效果评估 | 准备一组测试问题，量化评估检索与回答的质量 |
| L4 | 成本与性能 | token 统计、缓存、模型分级（小模型处理简单任务） |
| L4 | 可靠性与安全 | 超时、重试、降级、限流；提示词注入、输出校验、敏感信息 |
| L4 | 可观测性 | 记录每次调用的 prompt、token、耗时、工具调用链 |

## 2. 演示道具

- **API Key 只从环境变量读取**，绝不写进代码或配置文件；README 中说明需要设置哪些环境变量。
- **本地模型或 mock 模型**（必备）：优先提供 Ollama 等本地模型的配置，让没有 Key 的情况下也能运行大部分模块；
  测试中使用返回固定内容的 mock 模型，保证测试稳定、不花钱、不依赖网络。
- 向量数据库用 docker-compose 启动（或者使用内存实现），附带一份小而固定的示例文档集。
- 每个调用真实模型的模块，在 README 中注明大致的 token 消耗。

## 3. 必做实验

- 同一个任务，对比不同 prompt / 不同模型 / 不同参数的输出差异（输出有随机性，要说明这一点）。
- 工具调用：打印模型与应用之间的完整消息往返，看清楚「模型并不执行工具，只是返回调用意图」。
- RAG：对比「有检索」和「没有检索」的回答；故意让检索不到相关内容，观察模型的表现（幻觉）。
- 框架 vs 手写：同样的流程，用框架和直接调用 HTTP API 各实现一遍。

## 4. 常见的坑

- 输出不确定：测试中不能对真实模型的输出做精确断言，要用 mock 模型，或者只断言结构。
- 上下文长度：文档、历史、工具描述加在一起超过上下文窗口。
- 流式输出与工具调用、结构化输出的组合在不同框架中支持程度不同。
- 框架版本变化非常快，API 经常重命名，必须按 research.md 核对当前版本。
- 费用：循环调用、长上下文、Embedding 全量重建都会快速消耗 token。

## 5. 与用户熟悉的技术对照

| AI 应用概念 | 类似于 | 关键区别 |
|---|---|---|
| ChatClient / ChatModel | RestClient + 统一的远程调用抽象 | 输出不确定，需要校验与重试 |
| 工具调用 | RPC 的服务注册与调用 | 由模型决定调用哪个工具、传什么参数 |
| RAG | 搜索 + 模板渲染 | 检索质量决定回答质量 |
| Agent 循环 | 工作流引擎 / 状态机 | 下一步由模型决定，需要限制最大步数 |
| Embedding + 向量库 | 倒排索引 + 全文搜索 | 按语义相似度检索，而不是按关键词 |
