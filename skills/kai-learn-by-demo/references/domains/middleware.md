# Domain：中间件与存储

适用于：消息队列（Kafka、RocketMQ、RabbitMQ、Pulsar）、缓存（Redis）、数据库（MySQL、PostgreSQL）、搜索（Elasticsearch、OpenSearch）、图数据库（Neo4j）等独立部署的基础组件。

> 这份 domain 还没有经过实际项目的检验。第一次使用后，按 SKILL.md 第 7 步把经验沉淀回来。

## 1. 知识点维度

| 级别 | 维度 | 说明 |
|---|---|---|
| L1 | 部署与连接 | docker-compose 启动；客户端连接；最小的读写 / 收发 |
| L1 | 数据模型 | 核心概念（Topic/Partition、Key/数据结构、Index/Mapping、Node/Relationship）以及它们的约束 |
| L1 | 客户端 API | 原生客户端 + Spring 集成两种写法对照 |
| L2 | 典型场景 | 每个场景一个模块，例如消息的顺序 / 延迟 / 事务，缓存的分布式锁 / 排行榜，搜索的分词 / 聚合 |
| L2 | 可靠性语义 | 消息的投递语义与重复、缓存与数据库的一致性、写入的持久化级别 |
| L2 | 运维视角 | 管理命令、监控指标、常用的排查命令 |
| L3 | 存储与复制 | 日志结构、索引结构、主从 / 分区 / 副本、选主；用实验观察（如停掉一个节点） |
| L3 | 客户端内部 | 批量发送、连接池、重试、路由；手写一个简化的客户端协议或核心数据结构 |
| L4 | 容量与性能 | 压测方法、关键参数、瓶颈定位 |
| L4 | 高可用与故障 | 节点故障、网络分区、脑裂，以及对应的客户端表现 |

## 2. 演示道具

- **docker-compose**（必备）：单节点用于 L1/L2，多节点集群用于 L3/L4 的复制与故障实验；都要有健康检查。
- 带图形界面的管理工具（如 Kafka UI、RedisInsight、Kibana）一起放进 compose，方便观察。
- 故障注入：用 `docker compose stop/pause` 模拟节点故障，用 tc / toxiproxy 模拟网络延迟（可选）。
- 测试中使用 Testcontainers，让测试不依赖手动启动的环境。

## 3. 必做实验

- 至少一个「数据会丢 / 会重复」的实验，以及对应的防护配置。
- 至少一个「节点故障」的实验，观察客户端的表现（报错、重试、切换）。
- 与用户熟悉的方案做对照实验（例如 Kafka vs RocketMQ 的顺序消息）。

## 4. 常见的坑

- 默认配置偏向性能而不是可靠性（例如异步刷盘、acks、自动提交位点）。
- 客户端版本与服务端版本不匹配。
- 单节点下看不出来的问题（复制、分区、选主）。
- 容器中的网络地址与宿主机地址不同（advertised listeners 一类的配置）。
- Docker 镜像的架构（arm64 / amd64）与本机不匹配。
