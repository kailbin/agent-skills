# 通用规范（所有技术方向都要遵守）

## 1. 难度分级

| 级别 | 目录前缀 | 目标 | 典型内容 |
|---|---|---|---|
| L1 入门 | `level1-basic` | 跑通核心用法，建立直观认识 | 最小可运行示例、核心 API、默认配置 |
| L2 进阶 | `level2-advanced` | 组合使用，覆盖真实场景 | 多组件协作、自定义扩展点、异常与边界情况 |
| L3 原理 | `level3-principle` | 理解它为什么这样工作 | 源码导读、关键流程断点、**手写简化版实现** |
| L4 生产（可选） | `level4-production` | 能上生产 | 可观测性、调优、高可用、安全、成本 |

- 每个级别下按知识点拆分，编号为 `NN-主题`，例如 `01-service-discovery`，序号就是推荐的学习顺序。
- 一个模块只讲一个知识点。需要借助其他知识点时，直接依赖 common 模块，或者在注释中注明「前置：见 xx 模块」。
- **L3 是重点**：至少有一个模块要「手写一个简化版」，例如手写一个简易负载均衡器、简易 RPC 代理，
  并和真实实现做对照。

## 2. 注释规范

### 类 / 文件头注释（必写）

```java
/**
 * 【是什么】一句话说明这个类在示例中扮演的角色。
 *
 * 【为什么】这个技术 / 设计要解决什么问题；不用它会怎样。
 *
 * 【原理】核心机制，3~8 行。超过的话写一句摘要，再链接到 docs/NN-xxx.md。
 *
 * 【对比】（可选）和用户熟悉的方案对比，例如「Nacos vs Eureka」「SQS vs RocketMQ」。
 *
 * 【动手】（可选）建议用户改哪里、观察什么现象，例如「把超时时间改成 100ms，观察熔断日志」。
 */
```

### 行内注释

- 标注**关键行**，不要每一行都写注释。
- 用统一的标签，方便用户全局搜索：
  - `// 【原理】`：这行代码背后的机制
  - `// 【坑】`：容易出错的点，以及出错时的现象
  - `// 【对比】`：换成其他写法 / 方案会有什么不同
  - `// 【源码】`：对应框架源码的位置，例如 `LoadBalancerInterceptor#intercept`
  - `// 【生产】`：示例中为了简化而做的处理，在生产环境应该怎么做

### 禁止

- 只是复述代码的注释（`// 创建 list`）。
- 写出来就过时的版本细节（比如具体的小版本号），版本统一在 README 中声明。

## 3. 文档组织

```
<project-root>/
├── README.md                  # 学习路线总览（assets/README.template.md）
├── docs/
│   ├── 00-overview.md         # 技术全景：解决什么问题、核心概念、架构图（用 mermaid）
│   ├── NN-<topic>.md          # 长篇原理（assets/principle.template.md）
│   └── faq.md                 # 常见坑与排查方法汇总
├── docker-compose.yml         # 需要外部依赖时提供
└── <各级别模块>/
    └── <NN-topic>/README.md   # 模块级说明
```

模块 README 的固定结构：

1. **学习目标**：学完这个模块能回答哪些问题（2~4 个问题）
2. **运行**：命令 + 预期输出 / 现象
3. **代码导读**：建议按什么顺序看哪几个文件
4. **原理要点**：简短说明，长的链接到 `docs/`
5. **动手练习**：1~3 道题，要求修改代码并观察结果
6. **思考题**：偏架构、偏面试的问题，答案用 `<details>` 折叠

**什么时候单独写 md**：类头注释的【原理】写不下（超过 8 行），或者某个原理会被多个模块引用时，
就单独写到 `docs/`，并在代码中注明 `详见 docs/NN-xxx.md`。

## 4. 可运行性

- 运行模块不需要修改代码，最多改配置。
- 外部依赖都写进 `docker-compose.yml`，给出健康检查和端口说明。
- 需要付费的云资源时，优先使用本地模拟环境；必须用真实云资源时，提供清理脚本，并在 README 顶部提示费用。
- 端口统一规划，避免冲突，并在根 README 中列出端口表。

## 5. 没有 reference 时

路由表中没有对应 reference 的技术，先按下面的步骤拟定内容，再走正常流程：

1. 查官方文档，确定当前稳定版本和推荐的构建工具。
2. 列出 L1~L3 的知识点清单（L1 是官方 Getting Started 的范围，L2 是常用特性组合，L3 是核心机制）。
3. 列出 3~5 个最常见的坑。
4. 找出它和 Java 生态中最接近的对应物，用来做【对比】。

生成结束后提醒用户：这个方向可以补一个 reference，固化下来。
