# 通用规范（所有技术都要遵守）

## 1. 难度分级

| 级别 | 目录前缀 | 目标 | 典型内容 |
|---|---|---|---|
| L1 入门 | `level1-basic` | 跑通核心用法，建立直观认识 | 最小可运行示例、核心 API、关键配置 |
| L2 进阶 | `level2-advanced` | 组合使用，覆盖真实场景 | 各个集成点、多组件协作、扩展点、观测手段 |
| L3 原理 | `level3-principle` | 理解它为什么这样工作 | 源码导读、关键机制实验、**手写简化版 + 对照测试** |
| L4 生产（可选） | `level4-production` | 能上生产 | 调参方法、监控告警、故障场景、运维手段 |

- 每个级别下按知识点拆分，编号为 `NN-主题`，例如 `01-service-discovery`，序号就是推荐的学习顺序。
- 一个模块只讲一个知识点。需要借助其他知识点时，依赖 common 模块，或者在注释中注明「前置：见 xx 模块」。
- **L3 是重点**：至少有一个模块要「手写一个简化版」，并用**对照测试**（同样的输入同时驱动手写版和真实实现，逐步断言结果一致）证明理解正确。
- L3 尽量写成测试，不依赖外部服务，`test` 命令就能看到结果；时间相关的逻辑注入可控的时钟，不要真的 sleep。

## 2. 注释规范

### 类 / 文件头注释（必写）

```java
/**
 * 【是什么】一句话说明这个类在示例中扮演的角色。
 *
 * 【为什么】这个技术 / 设计要解决什么问题；不用它会怎样。
 *
 * 【原理】核心机制，3~8 行。超过的话写一句摘要，再链接到 docs/NN-xxx.md。
 *
 * 【对比】（可选）和用户熟悉的方案对比。
 *
 * 【动手】（可选）建议用户改哪里、观察什么现象。
 */
```

### 行内注释

- 标注**关键行**，不要每一行都写注释。
- 用统一的标签，方便用户全局搜索：
  - `// 【原理】`：这行代码背后的机制
  - `// 【坑】`：容易出错的点，以及出错时的现象
  - `// 【对比】`：换成其他写法 / 方案会有什么不同
  - `// 【源码】`：对应框架源码的位置，例如 `LoadBalancerInterceptor#intercept`
  - `// 【生产】`：示例中为了简化而做的处理，在生产环境应该怎么做

### 事实必须可靠

- 【原理】【源码】中提到的类名、方法名、默认值，都要核对过对应版本的源码（research.md 第 3 步）。
- 写不准的内容宁可不写，或者明确写成「建议运行 xx 验证」。

### 禁止

- 只是复述代码的注释（`// 创建 list`）。
- 写出来就过时的版本细节（比如具体的小版本号），版本统一在根 POM / README 中声明。

## 3. 文档组织

```
<project-root>/
├── README.md                  # 学习路线总览（assets/README.template.md）
├── docs/
│   ├── 00-overview.md         # 技术全景：解决什么问题、核心概念、架构图（mermaid）、与同类方案对比
│   ├── NN-<topic>.md          # 长篇原理（assets/principle.template.md）
│   └── faq.md                 # 常见坑与排查方法汇总，每条注明可以在哪个模块复现
├── docker-compose.yml         # 需要外部依赖时提供
└── <各级别模块>/
    └── <NN-topic>/
        ├── README.md          # 模块说明
        └── requests.http      # 有 HTTP 接口时提供，按实验顺序排列
```

模块 README 的固定结构：

1. **学习目标**：学完这个模块能回答哪些问题（2~4 个问题）
2. **运行**：命令
3. **实测结果**：实际运行得到的关键输出（不是预期），以及如何解读
4. **代码导读**：建议按什么顺序看哪几个文件
5. **原理要点**：简短说明，长的链接到 `docs/`
6. **动手练习**：1~3 道题，要求修改代码并观察结果
7. **思考题**：偏架构、偏面试的问题，答案用 `<details>` 折叠

**什么时候单独写 md**：类头注释的【原理】写不下（超过 8 行），或者某个原理会被多个模块引用时，
就单独写到 `docs/`，并在代码中注明 `详见 docs/NN-xxx.md`。

## 4. 可运行性

- 运行模块不需要修改代码，最多改配置。
- 观察类的接口要能「一次调用看到一段过程」，例如连续调用 N 次并返回每次的状态、耗时、执行线程，而不是只返回最终结果。
- 外部依赖都写进 `docker-compose.yml`，给出健康检查和端口说明。
- 需要付费的资源时，优先使用本地模拟；必须用真实资源时，提供清理脚本，并在 README 顶部提示费用。
- 端口统一规划（例如 L1 用 81xx、L2 用 82xx），在根 README 中列出端口表。
